harness — layout studies v0

Four layouts for the same app. Same shell, different answer to one question: what owns the screen — the chat, the files, or the thing you're building? Pick one, mark up the others, and this becomes the UI section of the BUILDME.

Shared vocabulary used in every mockup:

  • brain — the model, any OpenAI-compatible endpoint (default: LAN box).
  • panel — a resizable region that can host any view: chat session, file tree, viewer, editor, sqlite, log.
  • viewer — a plugin that renders a file type: md (edit), image/video, CAD (STL/STEP/OpenSCAD), circuit (KiCad/schematic), csv/sqlite.
  • mention — @file, /skill, #tool. Mentioned things become clickable and open in the other panel.

A · Commander two equal panels, each hosts any view

The Norton Commander answer. Both panels are peers; a panel is a chat, a tree, or a viewer depending on its active tab. Tab ⇄ swaps focus, the brain "opens X in the other panel". Function-key bar makes the whole thing keyboard-first.

B · Chat + dock chat is home, everything else docks beside it

Claude Code's UX, kept whole. The chat is the primary panel and never loses focus; the right side is a dock with a stacked tree + viewer. The brain opens files into the dock; you can pop the dock into a second chat when you need one.

C · Workbench the artifact owns the screen, chat is the console

For the sessions where you're iterating a circuit or a CAD part. The viewer is the big thing; chat sits at the bottom like a terminal console; tree is a slim rail. Toggle from any other layout with one key — this is a layout preset, not a different app.

D · Terminal-first one column, drawers on demand

The minimal one. Full-width chat exactly like Claude Code; tree, viewer, sessions are drawers that slide over the right third and go away. Least to build, easiest to ship as the web version first, and the natural mobile/narrow layout later.

Session navigator / rewind — F7 or Esc twice. Every message is a group (user turn + brain turn + its tool calls). Arrow to any group; Enter = continue from here (fork, old tail stays in the log), Del = drop the group, x = delete tool outputs but keep the text. This is also where you see token cost per group before compacting.

My take what I'd put in the BUILDME

Build A (Commander) as the shell — two panels, every panel is a view host — and ship B and C as layout presets on top of it (Ctrl+1/2/3), not as separate UIs. D is what A looks like when you collapse a panel, so it's free. The shell is one component: <Panel views=[chat, tree, viewer, editor, sql, log]>. Everything on your feature list becomes either a view, a tool the brain calls, or an overlay.

Why: your list has three things pulling in different directions (multiple sessions, navigate the tree, iterate a circuit). Only the two-peer-panels model makes all three first-class without a mode switch, and it's the aesthetic you already want.
